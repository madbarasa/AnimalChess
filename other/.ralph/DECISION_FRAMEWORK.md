# 游戏开发任务决策框架

> 本框架用于判断「普通会话修改」vs「Ralph 迭代」vs「Skill 封装」的适用场景。
> 每次接到游戏开发需求时，先按此框架分析，再选择执行策略。

## 一、任务分析维度

对每个子任务评估以下 4 个维度：

| 维度 | 问题 | 选项 |
|---|---|---|
| **依赖强度** | 改这个会影响其他模块吗？ | 高 / 中 / 低 |
| **验收难度** | 能否写自动化脚本判定对错？ | 难 / 中 / 易 |
| **风险等级** | 改坏了能轻松回滚吗？ | 高 / 中 / 低 |
| **迭代次数** | 预计需要几轮才能完成？ | 1次 / 2-3次 / 多次 |

## 三、快速对照表

| 任务类型 | 推荐方案 | 原因 |
|---|---|---|
| 架构重构 | 主会话 | 耦合深，需要连续推理 |
| 规则修复 | Ralph | 独立、验收明确、低风险 |
| 引擎核心改造 | 主会话 | 高风险，牵一发动全身 |
| UI/UX 优化 | Ralph 或 主会话 | 看是否影响逻辑层 |
| 批量配置调整 | Ralph | 重复性强，自动验收 |
| AI 算法迭代 | Ralph | 可独立测试，失败可回滚 |
| 性能优化 | 主会话 | 需要全局视角，容易改坏 |
| 代码审查 | Skill | 标准化流程，可复用 |
| 新增独立功能 | Ralph | 每项独立验收 |
| 紧急热修 | 主会话 | 需要快速连贯决策 |

## 四、执行前检查清单

在开始任何大规模改动前，必须完成：

- [ ] **任务拆分**：写入 `TASKS.md`，标明依赖关系和优先级
- [ ] **基线建立**：当前状态 commit，确保可回滚
- [ ] **验收脚本**：为每项任务写 `verify.mjs` MUST 段
- [ ] **进度文档**：建立 `PROGRESS.md` 模板，每轮强制更新
- [ ] **风险评估**：识别高风险项（如规则重构、AI 算法），优先主会话处理

---

## 五、Ralph 专项规则

当选择 Ralph 时，必须遵守：

1. **每轮只做 1-3 项**，不要贪多
2. **每项提交前必须跑 verify**，MUST 全绿才允许提交
3. **同一障碍连续 3 轮无法解决时，报告 blocker**
4. **worker 崩了不要空等**，直接接管主会话
5. **PROGRESS.md 必须包含下一轮起点**，否则交接失败

---

## 六、Token 效率原则

- **简单独立任务**：Ralph 更省（每轮重置避免上下文膨胀）
- **复杂依赖任务**：主会话更省（避免多轮协调开销）
- **混合策略最优**：架构设计用主会话，独立子任务扔给 Ralph
- **Skill 价值**：重复性标准化工作（代码审查、版本检查）用 Skill 封装

---

## 七、实战经验总结（来自 AnimalChess 项目）

### ✅ 成功的模式
- P1（规则修复 6 项）→ Ralph 完美运行，每项独立可验收
- P3/P4（工程优化 13 项）→ 主会话一口气推完，避免了 Ralph 第 5 轮的翻车

### ❌ 教训
- P2（架构重构 4 项）→ 耦合深，Ralph 第 5 轮 worker 崩了
- 如果重来：P1-P4 全部用主会话，省去 Ralph 的切换开销

### 💡 改进方向
- 高风险重构任务优先用主会话
- Ralph 适合「低风险 + 独立可验收」的任务
- 任务清单质量决定 Ralph 成败（TASKS.md 必须足够详细）
